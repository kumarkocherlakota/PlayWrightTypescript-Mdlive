# ADR-010: Healthcare data protection

- Status: Accepted
- Date: 2026-10-31

## Context

The reference domain is healthcare. Test artifacts (logs, screenshots, videos, traces, API
payloads) can contain Protected Health Information (PHI) and Personally Identifiable Information
(PII) if the environment contains real data.

## Decision

- **Never use real patient data.** Only synthetic data generated by builders; synthetic records are
  marked (e.g., a `TEST-` prefix or configured marker) so they are distinguishable.
- **Never log PHI/PII.** The `Redactor` masks names of known sensitive fields (name, DOB, SSN,
  MRN, member ID, address, phone, e-mail, diagnosis, insurance numbers) and common patterns.
- **Minimum necessary artifacts:** screenshots and videos are kept on failure only by default;
  traces retained on failure only; CI retention is short and configurable.
- **Privacy scenarios are first-class:** consent, role-based access, data masking in the UI,
  session timeout and sensitive-data exposure in API responses are tested (Phase 5/6).
- **FHIR validation** is optional and configurable (`healthcare.fhir`).
- **No compliance claims:** passing tests demonstrate tested behavior only. They do not establish
  HIPAA, GDPR or other regulatory compliance.

## Alternatives

| Option                              | Why not chosen                                       |
| ----------------------------------- | ---------------------------------------------------- |
| Disable all screenshots/videos      | Loses essential debugging evidence                   |
| Rely on environment being synthetic | Environments are sometimes refreshed from production |

## Reason

Defense in depth: avoid sensitive data at the source, mask on every output, and retain briefly.

## Consequences

- Some debugging information appears as `***` in reports; engineers reproduce locally with
  synthetic data.

## Trade-offs

Redaction may over-mask harmless values that look like sensitive patterns. Over-masking is the
accepted failure mode.
